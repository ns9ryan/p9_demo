# Platform-Game 开发规范

基于 `project-resources/docs/code-norm.md` 和 `core-api.md` 制定的项目规范。

---

## 一、代码量化限制

遵循以下量化限制（参考 code-norm.md）：

| 项 | 限制 | 说明 |
|---|---|---|
| 函数体行数 | ≤ 80 | Handler ≤ 40；`main`/`MustInit` ≤ 100 |
| 函数参数个数 | ≤ 5 | 不含 `ctx`、接收者；超过用 `Req`/`Options` 结构体 |
| 返回值个数 | ≤ 3 | 常见 `(T, error)` / `(T, int64, error)` |
| 嵌套深度 | ≤ 4 | `if/for/switch` 层数；用提前返回或抽函数优化 |
| 单文件行数 | ≤ 800 | 生成代码/纯路由表可到 1000 |
| 单行长度 | ≤ 120 | import/URL/DDL 字符串除外；用链式换行 |
| 圈复杂度 | ≤ 15 | 单个函数的决策分支数 |
| 局部变量 | ≤ 12 | 函数内 `:=`/`var` 声明的标识符 |
| 结构体导出字段 | ≤ 20 | 超过用子结构体（如分页、筛选、主体） |
| 包的导出函数 | 建议 ≤ 30 | 复杂包用子包处理 |

## 二、API 响应格式（core-api.md）

### 标准格式

**成功响应：**
```json
{
  "code": 0,
  "msg": "ok",
  "data": { ... }
}
```

**错误响应：**
```json
{
  "code": 401,
  "msg": "unauthorized"
}
```

### 实现细节

- 使用 `common/response/Response` 结构体
- 字段名必须为 `code`、`msg`、`data`
- HTTP 状态码与 `code` 相同
- 无返回体的接口 `data` 为 `null`
- 时间字段统一为 Unix 秒时间戳

### 错误码约定

| code | 含义 |
|------|------|
| 0 | 成功 |
| 400 | 参数错误 |
| 401 | 未登录/无效token |
| 403 | 无权限或资源被禁用 |
| 404 | 不存在 |
| 498 | access token 过期（用 refresh 重试） |
| 500 | 内部错误 |

## 三、模型设计原则

### Game 模型示例（符合规范）

Game 结构体严格控制在 **20 个导出字段**内：
- **身份标识**（3）：ID、GameCode、SourceID
- **外键关联**（3）：CategoryID、ProviderID、ChannelID
- **厂商标识**（2）：ProviderKey、SourceProviderKey
- **展示信息**（4）：NameI18n、ImageURL、SortNo、Status
- **源系统数据**（4）：SourceGameCode、SourceStatus、SourceImageURL、SourceSortNo
- **管理字段**（3）：IsDeleted、CreatedAt、UpdatedAt
- **扩展信息**（1）：SourceNameI18n

超出 20 个字段的场景用子结构体（见 `GameSourceInfo`、`GameFeatures`）。

### 字段命名规范

| 场景 | 规范 |
|------|------|
| 本地字段 | `GameCode`、`ProviderKey`、`NameI18n` |
| 源系统字段 | 前缀 `Source_`；如 `SourceGameCode`、`SourceStatus` |
| 枚举字段 | 使用标准值（见下表） |
| 多语言字段 | `JSONMap` 类型；key 为语言代码 |
| 时间字段 | `time.Time` 类型；JSON 自动转为 Unix 秒 |

### 标准枚举值

| 字段 | 值 | 说明 |
|------|---|-----|
| `status` | 1 | 启用 |
| | 2 | 停用 |
| `is_deleted` | 0 | 未删除（软删除） |
| | 1 | 已删除 |

## 四、同步服务设计原则（pkg/sync）

### Preview-Run-ReverseSync 三阶段模式

```go
// Preview：数据预检查，返回差异统计（无副作用）
func (s *Service) Preview(ctx context.Context, client Vendor) (*SyncPreviewResp, error)

// Run：执行同步，创建/更新/删除本地数据
func (s *Service) Run(ctx context.Context, client Vendor, autoApply bool) (*SyncRunResp, error)

// ReverseSync：逆向同步，软删除本地数据中远程不存在的项
func (s *Service) ReverseSync(ctx context.Context, client Vendor) (*SyncRunResp, error)
```

### 关键实现要点

1. **重复检测**：使用 `counterMap map[int64]int` 按 `SourceID` 检测重复远程数据
2. **外键验证**：同步前查询依赖实体（Category/Provider/Channel），确保 FK 约束
3. **软删除**：逆向同步时将本地不存在的远程数据标记为 `is_deleted=1`
4. **事务隔离**：同步操作在单个事务中完成，确保一致性

## 六、SQL 与查询优化

### 查询建议

1. **链式 WHERE**：每行一个条件，便于维护
   ```go
   q := db.WithContext(ctx).Model(&Game{})
   q = q.Where("is_deleted = ?", 0)
   q = q.Where("status = ?", 1)
   q = q.Where("category_id = ?", categoryID)
   ```

2. **预加载关联**：使用 `Preload` 而非 N+1 查询
   ```go
   db.WithContext(ctx).Preload("Category").Preload("Provider").Find(&games)
   ```

3. **索引利用**：foreign key 查询应使用复合索引
   - `idx_game_source_id_is_deleted` 用于 FK 查询与软删除过滤

## 七、常见问题与改进建议

### Q1：Model 中文字段太多如何处理？
A：按维度拆分。Game 的源系统信息用 `SourceXxx` 前缀；响应 DTO 中按需组合。

### Q2：Handler 超过 40 行怎么办？
A：拆成多个小函数（校验、转换、调用服务、返回）。Handler 只做编排。

### Q3：同步时如何避免 FK 约束冲突？
A：同步顺序必须是 Category → Provider → Channel → Game → Currency。每个阶段都用 `validateForeignKeys()` 前置校验。

### Q4：时间字段如何处理？
A：模型用 `time.Time`；JSON 序列化自动转为 Unix 秒。
